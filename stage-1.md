# Stage 1 - Ingestion Design

## 1. Goal

The ingestion stage accepts a customer's document, creates a durable job record, validates that the upload is safe and processable, and starts the processing pipeline only after the file is fully uploaded and accepted.

This stage must stay simple and reliable because every later pipeline stage depends on the job state and metadata it creates.

## 2. Requirements Covered

Stage 1 covers these requirements from `requirements.md`:

- Accept PDF uploads up to 300 MB.
- Generate a unique job ID.
- Validate tenant identity, schema selection, file type, file size, checksum, and page-count limits.
- Scan uploaded objects for malware before any PDF parsing or downstream processing.
- Persist the primary file in S3.
- Track job state in a durable database.
- Start validation automatically from the S3 upload event.
- Define the latency clock as starting when the upload is validated and accepted.
- Consume tenant processing quota only after upload acceptance.
- Preserve auditability, security, and observability from the first customer interaction.

## 3. Recommended Flow

### 3.1 Create Job

Customer calls:

```http
POST /v1/jobs
X-API-Key: <tenant-api-key>
Authorization: Bearer <signed-jwt>
```

Request body:

```json
{
  "client_request_id": "8f7f6ad2-0df4-4c1d-9e7a-4a34f438b6e2",
  "tenant_id": "tenant_123",
  "schema_id": "invoice_v1",
  "filename": "invoice-batch-001.pdf",
  "content_type": "application/pdf",
  "declared_size_bytes": 184238012,
  "checksum_sha256": "required-sha256-checksum",
  "webhook_id": "wh_default"
}
```

The API validates the API key, signed JWT, tenant, schema, declared file metadata, required checksum, `client_request_id`, quota eligibility, admission-control limits, and webhook configuration. If accepted, it creates a job record in DynamoDB and returns a presigned S3 POST target.

Quota is checked at this point to fail fast if the tenant is clearly over limit, but it is not consumed yet. Quota is consumed only after the uploaded object passes validation and the job is accepted.

Response:

```json
{
  "job_id": "job_01HW...",
  "status": "UPLOAD_PENDING",
  "upload_url": "https://document-ai-input.s3-accelerate.amazonaws.com",
  "upload_method": "POST",
  "upload_fields": {
    "key": "tenant=tenant_123/jobs/job_01HW/input/original.pdf",
    "Content-Type": "application/pdf",
    "x-amz-server-side-encryption": "aws:kms",
    "x-amz-server-side-encryption-aws-kms-key-id": "arn:aws:kms:us-east-1:123456789012:key/tenant-123-cmk",
    "x-amz-meta-tenant-id": "tenant_123",
    "x-amz-meta-job-id": "job_01HW...",
    "x-amz-meta-checksum-sha256": "required-sha256-checksum"
  },
  "upload_expires_at": "2026-05-14T12:30:00Z",
  "object_key": "tenant=tenant_123/jobs/job_01HW/input/original.pdf"
}
```

The upload URL TTL is 30 minutes. S3 Transfer Acceleration is enabled by default in v1 to improve upload reliability for geographically distributed customers. In v2, this can become tenant-configurable or geography-aware to reduce unnecessary acceleration cost.

The presigned POST policy must include these upload guardrails:

- `content-length-range`: 1 byte to 300 MB.
- Exact `Content-Type`: `application/pdf`.
- Exact object key generated by the platform.
- Required tenant/job metadata.
- Required checksum metadata.
- Required server-side encryption: `aws:kms`.
- Required tenant KMS key ID.

If the customer omits or changes these fields, S3 rejects the upload before the object is stored.

### 3.2 Upload Document

The customer uploads the PDF directly to S3 using the presigned POST target.

The S3 object key is generated by the platform, not supplied by the customer:

```text
s3://document-ai-input/tenant=<tenant_id>/jobs/<job_id>/input/original.pdf
```

This prevents path traversal, key collisions, and accidental cross-tenant placement.

### 3.3 S3 Event Triggers Security and Validation

After the upload completes, S3 emits an `ObjectCreated` event for the platform-generated object key. The event triggers the ingestion validation Lambda.

The validation Lambda first performs metadata-only checks:

- The job exists and belongs to the tenant.
- The object exists in the expected S3 location.
- The object size is greater than zero and does not exceed 300 MB.
- The object content type is `application/pdf`.
- The checksum matches the required checksum supplied at job creation.
- The upload occurred before the 30-minute upload URL TTL expired.
- The object was encrypted with the tenant's expected KMS key.
- The selected schema belongs to the tenant and is active.

The platform then waits for the GuardDuty Malware Protection for S3 scan result before parsing the file. Only objects tagged or reported as clean can continue. Malicious, failed, or unsupported scan results move the job to a rejected/quarantined state and do not consume processing quota.

After the malware scan is clean, the validation Lambda runs a fast PDF structural probe using a lightweight PDF tool such as `qpdf` or `pdfinfo` packaged with the Lambda/container image. This probe validates:

- The first bytes and structure are consistent with a PDF.
- The file is readable enough for the next stage.
- The page count is between 1 and 1,000 pages.
- The PDF is not obviously encrypted/password-protected.

The tenant still must have processing quota available after these checks.

If metadata validation, malware scan, PDF structural validation, page-count validation, and quota check all pass, the job transitions to `ACCEPTED`, tenant quota is consumed, and the platform starts the processing workflow.

The platform records `accepted_at` at this point. This is the start of the case study's 5-minute latency clock.

If validation fails, the job transitions to `UPLOAD_REJECTED`, `MALWARE_REJECTED`, or `SECURITY_SCAN_FAILED` depending on the reason. Rejected uploads do not consume processing quota. If a job is accepted and later cancelled or fails deeper in the pipeline, the customer is billed for the partial pipeline usage already consumed.

## 5. Job State Model for Ingestion

| State | Meaning | Owner |
|---|---|---|
| `UPLOAD_PENDING` | Job created, upload URL issued, file not accepted yet | Submission Lambda |
| `UPLOAD_EXPIRED` | Upload was not completed within TTL | Reconciliation job |
| `UPLOAD_RECEIVED` | S3 object-created event observed and validation is in progress | Validation Lambda |
| `MALWARE_SCAN_PENDING` | Waiting for GuardDuty Malware Protection scan result | Validation Lambda / GuardDuty |
| `MALWARE_REJECTED` | Malware scan found malicious content | GuardDuty / Validation Lambda |
| `SECURITY_SCAN_FAILED` | Malware scan failed, timed out, or returned unsupported status | GuardDuty / Validation Lambda |
| `UPLOAD_REJECTED` | Object failed validation | Validation Lambda |
| `ACCEPTED` | Object passed metadata, malware, page-count, and quota checks; quota consumed; workflow can start | Validation Lambda |
| `PROCESSING_STARTED` | Step Functions execution has started | Validation Lambda / Orchestrator |
| `FAILED` | Unrecoverable ingestion failure | Validation Lambda |

`ACCEPTED` is the key boundary. Before this state, the platform has a potential upload. After this state, the platform has a billable processing job.

## 6. Client Request Idempotency Design

Idempotency is mandatory in ingestion because customers may retry API calls and uploads during network failures.

### 6.1 Job Creation

The customer sends a `client_request_id` in the `POST /v1/jobs` body.

The platform stores:

- `tenant_id`
- `client_request_id`
- `request_hash`
- `job_id`
- `created_at`
- `expires_at`

If the same tenant sends the same `client_request_id` with the same request body, return the original job. If the same tenant sends the same `client_request_id` with a different request body, reject it with a conflict error.

### 6.2 Upload Validation

S3 may deliver duplicate object-created events, and the validation Lambda may retry after timeouts. Upload validation must therefore be idempotent.

If the job is already `ACCEPTED` or `PROCESSING_STARTED`, return the existing accepted state and do not start another workflow. Use a DynamoDB conditional update to ensure only one caller can transition the job into `ACCEPTED`.

### 6.3 Workflow Start

The Step Functions execution name should be derived from the job ID:

```text
document-ai-<job_id>
```

This prevents duplicate workflow starts even if the validation Lambda retries after a timeout.

## 7. Admission Control and Tenant Fairness

Stage 1 is the right place to protect the platform from burst unfairness. A single tenant should not be able to consume all ingestion capacity during a 50,000-document burst.

Controls:

- Enforce global API throttles at API Gateway/WAF.
- Enforce tenant-level request rate limits in the Lambda authorizer or submission Lambda.
- Use a token-bucket model per tenant and per tenant tier.
- Return `429 Too Many Requests` when a tenant exceeds its short-window rate.
- Include `Retry-After` and exponential-backoff guidance in the response.
- Keep separate limits for job creation, upload validation, and accepted processing starts.
- Check quota at job creation for fast rejection, but consume quota only after upload validation succeeds.

Example response:

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 30
```

```json
{
  "error": "tenant_rate_limited",
  "message": "Tenant ingestion rate exceeded. Retry with exponential backoff.",
  "retry_after_seconds": 30
}
```

Fairness should use both rate and concurrency:

- `max_create_job_rps` limits upload intent creation.
- `max_pending_uploads` limits abandoned upload pressure.
- `max_accepts_per_minute` limits how quickly a tenant can enter the expensive processing pipeline.
- `max_active_jobs` limits concurrent downstream work.

This prevents one tenant's bulk upload from starving other tenants while still allowing controlled bursts.

## 8. DynamoDB Key Design

The job table must avoid hot partitions during 50,000-document bursts. Do not key all writes only by `tenant_id`.

Recommended single-table sketch:

| Access pattern | Item type | PK | SK | Notes |
|---|---|---|---|---|
| Get job by ID | Job metadata | `JOB#<job_id>` | `META` | Main lookup path; distributed because `job_id` is high-cardinality. |
| Retry-safe create | Client request | `CLIENTREQ#<tenant_id>#<client_request_id>` | `REQUEST` | TTL 24h; stores request hash and job ID. |
| Resolve S3 event to job | Object mapping | `OBJECT#<sha256(bucket/key)>` | `JOB#<job_id>` | Lets validation map object-created event to job safely. |
| Tenant timeline | Job metadata GSI | `TENANT#<tenant_id>#SHARD#<0-31>` | `CREATED#<timestamp>#JOB#<job_id>` | Write-sharded tenant listing avoids hot tenant partitions. |
| Quota/rate counters | Counter item | `QUOTA#<tenant_id>#<window>#SHARD#<0-63>` | `COUNTER` | Sharded counters avoid hot writes during bursts. |
| Usage ledger | Ledger event | `JOB#<job_id>` | `USAGE#<stage>#<timestamp>` | Per-stage cost and elapsed-time records. |


## 9. Validation Policy

Validation is intentionally split into lightweight ingestion validation and deeper pre-processing validation.

### 9.1 Ingestion Validation

Ingestion should validate:

- Tenant and authorization.
- Schema ownership and active status.
- File exists in expected S3 key.
- File size is within the 300 MB limit.
- File extension, content type, and magic bytes are consistent with PDF.
- Checksum is present and matches the value supplied at job creation.
- GuardDuty Malware Protection scan result is clean.
- Page count is within the 1,000-page limit.
- S3 object is encrypted with the expected tenant KMS key.
- Upload occurred before the 30-minute presigned POST policy expired.

### 9.2 Deferred Validation

The next pre-processing stage should validate:

- Deeper PDF readability.
- Full encryption/password-protection behavior.
- Corruption or malformed structure.
- Digital-text vs scanned/hybrid classification.
- Whether the document needs image enhancement before OCR.

This split keeps ingestion fast while still preventing bad files from entering expensive OCR and LLM stages.

## 10. Security and Compliance

Security starts at ingestion because this is where customer data enters the platform.

Controls:

- Authenticate every API request using an API key plus a signed JWT bearer token.
- Authorize tenant access to the selected schema and job.
- Generate object keys server-side.
- Encrypt input objects with per-tenant KMS CMKs.
- Enforce TLS for upload and API traffic.
- Deny non-TLS S3 access with an `aws:SecureTransport=false` bucket policy condition.
- Enforce TLS 1.2 or newer on API Gateway custom domains/security policy.
- Block public S3 access.
- Use least-privilege IAM for API, Lambda, S3, DynamoDB, and Step Functions.
- Scan uploaded S3 objects for malware before acceptance.
- Do not log raw document text, upload URLs, or unmasked sensitive metadata.
- Store webhook secrets in Secrets Manager.
- Emit audit events for job creation, upload completion, malware scan result, validation rejection, and workflow start.
- Capture AWS API activity in CloudTrail.
- Use pre-registered webhook endpoints in v1. Jobs reference a `webhook_id` instead of supplying arbitrary callback URLs.
- Expose ingestion through a public API protected by WAF in v1. PrivateLink is deferred to v2 for tier-based enterprise access.

Compliance impact:

- GDPR access and erasure workflows need the tenant ID, job ID, and object key created here.
- SOC 2 evidence starts with auditable job creation and upload acceptance events.
- Tenant isolation depends on consistent tenant-scoped keys, IAM conditions, and authorization checks from this stage onward.

### 10.1 JWT Trust Chain

JWTs are issued by the platform identity service backed by Amazon Cognito or an external OIDC-compatible IdP approved at tenant onboarding.

- Use asymmetric signing (`RS256` or `ES256`); publish verification keys via a JWKS endpoint.
- Keep JWT lifetime short (5–15 minutes for machine-to-machine calls); store private signing keys in KMS or Secrets Manager.
- Validate `iss`, `aud`, `exp`, `kid`, tenant claim, and allowed scopes in the Lambda authorizer.
- Never trust `tenant_id` from the request body unless it matches the tenant resolved from the API key and JWT claims.

### 10.2 Tenant KMS Isolation

Use a per-tenant CMK for customer document data in v1. At minimum, every input object, intermediate object, output object, and tenant-scoped artifact must be encrypted under the tenant's CMK or a data key derived from that tenant boundary.

Controls:

- Store `tenant_kms_key_arn` in tenant configuration.
- Include the expected tenant KMS key in the presigned POST policy.
- Validate `SSEKMSKeyId` on the uploaded object before acceptance.
- Scope IAM permissions so processing roles can decrypt only for the tenant/job being processed.
- Use encryption context such as `tenant_id` and `job_id` where supported.
- On GDPR erasure, delete tenant objects and, where contractually appropriate, schedule tenant-key deletion after retention/legal-hold checks.

This is stronger than a single platform CMK because it gives each tenant a cryptographic boundary, not only an IAM boundary.

### 10.3 Immutable Audit Records

CloudWatch Logs and normal S3 objects are not enough for SOC 2-grade audit immutability. The ingestion stage must send audit events to an immutable audit path:

```text
Application audit event -> EventBridge -> Firehose -> S3 audit bucket
```

Audit bucket: S3 Object Lock in compliance mode, platform-managed KMS key separate from tenant document keys.

Audit events include: `tenant_id`, `job_id`, `client_request_id_hash`, `actor`, `event_type`, `previous_state`, `new_state`, `timestamp`, `source_ip`, `request_id`, `object_key_hash`, `malware_scan_status`, `validation_failure_reason`.

Do not write raw document text or presigned URLs to audit events.

### 10.4 GDPR Erasure vs. Immutable Audit

Immutable audit records and GDPR erasure are not in conflict if the audit stream never stores PII or document content.

Separation rule:

- Customer PII and document content live only in tenant-encrypted data objects and tenant-scoped derived artifacts.
- Audit records store operational facts only: tenant ID, job ID, event type, timestamps, state transitions, actor IDs, hashed object keys, hashed client request IDs, and validation outcomes.
- Filenames, document text, extracted fields, presigned URLs, emails, SSNs, and raw customer metadata are not written to immutable audit records.

Erasure behavior:

- For GDPR erasure, delete tenant data objects, intermediate artifacts, outputs, and indexes that contain customer content.
- If the tenant contract permits crypto-shredding, disable/schedule deletion of tenant-specific keys after retention and legal-hold checks.
- Keep immutable audit records because they contain non-PII operational evidence needed for SOC 2 and security investigations.

This gives us verifiable deletion of customer content while preserving tamper-resistant evidence that a job existed and how it was handled.

### 10.5 Automatic PII Controls for Logs

Emit-time scrubbing is the primary control: use a structured logging library with pattern-based redaction of email, SSN-like values, phone numbers, access tokens, presigned URLs, and free-form filenames before logs leave the Lambda process. A CloudWatch Logs subscription filter feeding a Comprehend-backed inspection Lambda acts as the verification layer to detect any leakage that bypasses emit-time scrubbing.

## 12. Cost Considerations

Ingestion should remain a small percentage of total cost. The major cost drivers are OCR and LLM extraction, so the ingestion stage must prevent bad or unauthorized documents from reaching those stages.

Cost controls:

- Use direct S3 upload instead of proxying files through Lambda.
- Keep Lambda work short and metadata-focused.
- Use DynamoDB On-Demand to absorb bursts without overprovisioning.
- Use S3 Transfer Acceleration by default in v1; revisit in v2 with a tenant/geography-aware policy.
- Expire abandoned uploads and incomplete jobs.
- Reject invalid files before OCR or LLM calls.
- Reject malware and over-limit page counts before OCR or LLM calls.
- Track accepted jobs separately from created upload intents so billing and latency metrics are accurate.
- Consume tenant quota only after upload validation succeeds.
- Bill for partial pipeline usage after acceptance if the job is cancelled or fails after consuming downstream resources.
- Maintain a per-job usage ledger that is updated at each pipeline stage with elapsed time, AWS service usage, model tokens, estimated cost, and billable status.

### 12.1 Usage and Billing Ledger

Every job has a usage ledger keyed by `tenant_id` and `job_id`. The ledger is updated as the job moves through the pipeline.

Minimum ledger fields:

- `stage`
- `started_at`
- `completed_at`
- `elapsed_ms`
- `service_name`
- `usage_quantity`
- `usage_unit`
- `estimated_cost_usd`
- `billable`
- `billing_reason`

Billing policy:

- Before `ACCEPTED`, the platform does not consume tenant processing quota.
- Invalid uploads rejected during ingestion do not consume processing quota.
- After `ACCEPTED`, each stage records real usage and estimated cost as it completes.
- If the job is cancelled or fails after acceptance, the user is charged for the billable usage incurred up to that point.
- Final billing uses the recorded usage ledger, reconciled against AWS cost data where needed.

## 13. Approximate Ingestion Cost per Document

Ingestion is a small fraction of total per-document cost. The two meaningful cost drivers at this stage are:

| Step | Approx cost (300 MB worst case) | Notes |
|---|---|---|
| S3 Transfer Acceleration | ~`$0.012` (`$0.04/GB`) | Outside the 5-minute SLA; customer upload time not counted. |
| GuardDuty Malware Protection | ~`$0.027` (`$0.09/GB + $0.215/1K objects`) | Asynchronous; job not accepted until scan is clean. |
| All other ingestion steps (Lambda, DynamoDB, API Gateway, Step Functions start) | `<$0.001` combined | Lambda is metadata-only; no file bytes pass through it. |

Total ingestion cost per document: under `$0.04` at the 300 MB ceiling. The remaining cost budget is consumed by OCR and LLM stages.

## 14. Failure Handling

| Failure | Handling |
|---|---|
| Customer retries `POST /v1/jobs` | Return same job if `client_request_id` and request hash match |
| Customer uploads too late | Mark job `UPLOAD_EXPIRED`; require new job |
| Customer uploads wrong file type | Mark job `UPLOAD_REJECTED`; retain for audit/debug for 7 days, then cold storage for 21 days, then delete |
| Customer uploads file over 300 MB | Mark job `UPLOAD_REJECTED`; retain for audit/debug for 7 days, then cold storage for 21 days, then delete |
| Customer uploads file with checksum mismatch | Mark job `UPLOAD_REJECTED`; do not consume quota |
| GuardDuty reports malware | Mark job `MALWARE_REJECTED`; quarantine object; do not consume quota |
| GuardDuty scan fails or times out | Mark job `SECURITY_SCAN_FAILED` or keep pending with bounded retry; do not consume quota |
| PDF exceeds 1,000 pages | Mark job `UPLOAD_REJECTED`; do not consume quota |
| Tenant exceeds rate limit | Return `429` with `Retry-After`; do not create extra jobs |
| Validation Lambda times out or returns retryable error | Use Lambda async retry with exponential backoff and full jitter: retry after roughly 1 minute, then roughly 2 minutes, capped at 2 async attempts; conditional updates prevent duplicate acceptance. If retries are exhausted, send the invocation record to the on-failure destination or SQS DLQ with `tenant_id`, `job_id`, object key hash, failure reason, and retry count for replay |
| Step Functions start fails | Retry; if still failing, keep job accepted but mark `workflow_start_pending` for replay |
| Duplicate S3 event arrives | Re-read job state; no-op if already accepted, rejected, or started |
| S3 event is delayed or missed | Reconciliation job scans pending uploads and triggers validation |
| Created job never receives upload | TTL/reconciliation marks `UPLOAD_EXPIRED` |
| Job cancelled after acceptance | Stop downstream work where possible; bill partial usage already consumed |

## 15. Resolved Stage 1 Decisions

These decisions are now part of the Stage 1 design:

1. Use `client_request_id` rather than exposing an `Idempotency-Key` header.
2. Retain client request idempotency records for 24 hours.
3. Retain rejected uploads for 7 days for audit/debugging, then move to cold storage for 21 days, then delete.
4. Use API keys plus signed JWT bearer tokens for customer authentication.
5. Use public API plus WAF in v1; defer PrivateLink to v2 enterprise/tier-based access.
6. Use pre-registered webhook endpoints in v1.
7. Track elapsed time and estimated cost at each pipeline stage.
8. Bill the user for billable usage incurred up to the point of cancellation or failure after acceptance.
9. Gate acceptance on malware scan clean result.
10. Use presigned POST policy conditions for content length, content type, checksum metadata, and tenant SSE-KMS key.
11. Use per-tenant KMS CMKs for document data.
12. Send audit events to immutable S3 Object Lock storage through EventBridge and Firehose.
13. Enforce tenant fairness with rate limits, `429`, and backoff.
14. Use high-cardinality DynamoDB keys and sharded tenant/quota indexes to avoid hot partitions.
15. Validate page count in ingestion before quota is consumed.
16. Use emit-time log scrubbing plus subscription-based PII detection.
17. Define JWT issuer, signing-key storage, JWKS verification, short token TTL, and key rotation.
18. Keep immutable audit records PII-free so GDPR erasure deletes customer content while preserving SOC 2 evidence.
19. Enforce `aws:SecureTransport` on S3 and TLS 1.2+ on API Gateway.
